# DXF from Photo

Инструмент превращает фото эскиза детали (с рукописными размерами) в DXF-файлы:

1. `*_draft.dxf` — черновой контур, распознанный по фотографии автоматически (геометрия + классификация отверстий/вырезов, без проверенных размеров).
2. `*_dimensioned.dxf` — контур с профессионально нанесёнными размерными линиями, диаметрами отверстий и осевыми метками, на основе введённых пользователем проверенных размеров.

Дополнительно: `ocr_dimensions.py` — локальное (без внешних API) распознавание рукописных размерных чисел на фото как вспомогательных кандидатов для проверки оператором.

## Важно

Черновой DXF (`draft`) нельзя отправлять на резку без проверки размеров человеком. Автоматическое распознавание рукописного эскиза даёт приблизительную топологию (форму) и приблизительные размеры-кандидаты, а не точные размеры для производства. Итоговые размеры всегда должен подтверждать оператор.

## Установка

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

Для OCR также нужен установленный `tesseract` (работает полностью локально, без интернета и внешних API):

```bash
# macOS
brew install tesseract tesseract-lang
# Ubuntu/Debian
sudo apt-get install tesseract-ocr tesseract-ocr-rus
```

## Использование

### 1. Черновой DXF из фото (v3)

```bash
python src/photo_to_draft_dxf.py examples/sketch.jpg output/draft.dxf --scale-mm=1830 --debug-dir=output/debug
```

Скрипт (v3):
- автоматически выравнивает перспективу листа (deskew), если в кадре виден его край;
- переводит фото в градации серого, усиливает контраст (CLAHE), бинаризует;
- находит полное дерево контуров (`RETR_TREE`): внешний контур детали, круглые отверстия, замкнутые вырезы, открытые вырезы на краю листа;
- классифицирует каждый контур по роли (`OUTER`, `HOLE_ROUND`, `CUTOUT`, `OPEN_CUTOUT`) и по геометрической правдоподобности (circularity, касание края, размер относительно детали);
- подтверждает круглые отверстия через `HoughCircles` внутри ROI-маски самой детали (не по всему кадру — это убирает большинство ложных срабатываний от фона/стола/почерка);
- в strict-режиме (по умолчанию включён) отсекает объекты с низкой уверенностью, вместо того чтобы засорять DXF мусорными вырезами;
- сохраняет результат в DXF со слоями `CUT`, `HOLES`, `CUTOUTS`, `OPEN_CUTOUTS`, `HOLES_LOW_CONF`, `CENTER`, `TEXT`;
- при `--debug-dir` сохраняет промежуточные изображения (deskew, thresholding, overlay с классификацией) и `recognition_report.json` с подробным списком найденных объектов и их уверенностью.

Флаги:
- `--no-hough` — отключить проверку через Hough (только findContours).
- `--include-hough-only` — включить в DXF круги, найденные Hough, но не подтверждённые findContours (менее надёжно, для отладки).
- `--no-strict` — отключить фильтрацию по confidence (выводить все найденные объекты, включая низкоуверенные).

### 2. Распознавание рукописных размеров (локально, без API)

```bash
python src/ocr_dimensions.py examples/sketch.jpg --debug-dir=output/ocr_debug
```

Скрипт:
- находит текстовые зоны на фото через MSER + морфологическую группировку близких боксов;
- прогоняет каждую зону через локальный Tesseract OCR (whitelist только цифр и разделителей);
- фильтрует результат по правдоподобности (число 1-5 значащих цифр);
- сохраняет `ocr_dimensions.json` со списком кандидатов `{bbox, raw_text, parsed_value_mm, ocr_confidence}` и `ocr_overlay.png` с визуализацией.

**Честная граница возможностей**: Tesseract — универсальный OCR-движок, обученный в основном на печатном тексте. На инженерном рукописном почерке (тонкая ручка, наклон, цифры вплотную к линиям и стрелкам чертежа) точность распознавания низкая — по тестам на реальных эскизах корректно распознаётся лишь малая часть чисел, иногда 0 из 15-20. Результат — кандидаты для проверки оператором, не окончательные размеры. Промышленное качество распознавания рукописного текста требует специализированной handwriting-модели (например TrOCR-handwritten) с дообучением на собственном датасете — такая модель весит около 1.3GB и требует среды с достаточной памятью для инференса; работа над этим — предмет отдельного этапа roadmap (см. ниже).

### 3. DXF с профессиональными размерами

Размеры задаются вручную в JSON-файле (после того как оператор проверил их по фото, кандидатам OCR или физическому шаблону):

```bash
python src/build_dimensioned_dxf.py examples/part_spec.json output/dimensioned.dxf
```

Пример `part_spec.json`:

```json
{
  "width": 1830,
  "height": 381,
  "holes": [
    {"x": 52, "y": 22, "d": 10},
    {"x": 485, "y": 22, "d": 10},
    {"x": 938, "y": 22, "d": 10},
    {"x": 1391, "y": 22, "d": 10},
    {"x": 1786, "y": 22, "d": 10},
    {"x": 52, "y": 359, "d": 10},
    {"x": 485, "y": 359, "d": 10},
    {"x": 938, "y": 359, "d": 10},
    {"x": 1391, "y": 359, "d": 10},
    {"x": 1786, "y": 359, "d": 10}
  ]
}
```

Скрипт строит контур, отверстия, размерные цепочки по X, вертикальные размеры, отступы от кромок и подписи диаметров — аналогично тому, как это делает чертёжник вручную.

## Архитектура

```
src/
  geometry.py            — общие функции построения DXF (линии, стрелки, размеры, текст)
  photo_to_draft_dxf.py  — распознавание контура/отверстий/вырезов по фото → draft.dxf (v3)
  ocr_dimensions.py      — локальное OCR-распознавание рукописных размерных чисел (кандидаты)
  build_dimensioned_dxf.py — построение точного DXF по проверенным размерам → dimensioned.dxf
examples/
  sketch.jpg             — пример фото эскиза (добавьте свой)
  part_spec.json         — пример проверенных размеров
```

## Roadmap (следующие уровни)

- Уровень 1 (готово): параметрический ввод размеров → точный DXF.
- Уровень 2 (готово, v3): устойчивое распознавание контура, отверстий и вырезов по фото с классификацией по уверенности, deskew листа, ROI-ограниченный Hough — без ложных срабатываний на чистых эскизах.
- Уровень 3 (готово, черновой): локальное OCR-распознавание рукописных цифр как кандидатов для проверки (без внешних API). Точность ограничена возможностями Tesseract на рукописном тексте — задокументировано явно.
- Уровень 4 (план): дообучение специализированной handwriting-OCR модели на собственном датасете сканов эскизов для повышения точности распознавания рукописных чисел.
- Уровень 5 (план): автоматическая привязка распознанных чисел к конкретным линиям/сторонам/дугам контура (geometry-text linking) без участия оператора.

## Отчёт по эксперименту с обученной цифро-моделью (v4, частично)

Проведён эксперимент по максимальному приближению к распознаванию рукописных цифр без внешних API:

1. **Обучена собственная CNN на MNIST** (`models/digit_cnn_mnist.pt`, 427KB) — точность **98.6%** на изолированных, прямых, отдельно стоящих цифрах. Модель обучалась локально в песочнице (3 эпохи, ~70 секунд на CPU).
2. **Протестирована на реальном фото эскиза.** Результат: изолированный подход не сработал — рукописные размеры на реальных фото написаны:
   - под углом 60-85° (вдоль стрелки размерной линии, не горизонтально),
   - слитно (курсивное написание, цифры соединены между собой, как в скорописи, а не печатными раздельными знаками),
   - вплотную к линиям чертежа (стрелки и размерные линии пересекают текст).
3. **Выравнивание угла помогло частично** — после поворота на -80° текст стал визуально читаем человеком ("433мм"), но автоматическая сегментация на отдельные цифры (по компонентам связности или по морфологической очистке линий) не дала чистого результата: линии чертежа и цифры сливаются в один связный контур, что делает MNIST-модель (обученную на изолированных цифрах) неприменимой напрямую.

**Честный вывод**: задача распознавания слитных наклонных цифр вплотную к графике чертежа — это задача уровня "sequence recognition" (как handwriting-OCR), а не "classification" (как MNIST). Для её решения одной классификационной CNN недостаточно — нужна либо: (а) ручная более точная сегментация на этапе фотографирования эскиза (писать цифры разборчиво, горизонтально, без пересечения со стрелками), либо (б) дообучение sequence-модели (CRNN/TrOCR) на датасете именно таких наклонных инженерных чисел, что требует размеченного датасета в 200+ примеров и GPU-среды для приемлемого времени обучения.

Текущий практический максимум: `ocr_dimensions.py` выдаёт кандидатов с низкой достоверностью для проверки оператором; `models/digit_cnn_mnist.pt` — готовый строительный блок (обучен и протестирован), который может быть переиспользован в будущем pipeline после решения задачи сегментации.

## Универсальная привязка размеров (v5)

`src/dimension_linker.py` связывает OCR-кандидаты с геометрией независимо от угла надписи. Модуль локально ищет размерные и выносные линии через HoughLinesP, V-образные стрелки, определяет направление размера, привязывает концы к вершинам, рёбрам и окружностям и классифицирует размер как линейный, диаметр, радиус или угол. Размерные стрелки задают измеряемые границы, а выносные линии связывают их с элементами детали — поэтому привязка строится по графическим связям, а не только по близости текста.

```bash
python src/dimension_linker.py photo.jpg ocr_dimensions.json recognition_report.json --debug-dir=output/link_debug
```

Результат сохраняется в `dimension_links.json` и `dimension_links.png`. Автоматически принимаются только связи с достаточной совокупной уверенностью OCR + линия + стрелки + геометрия; неоднозначные случаи получают статус `review` или `unresolved`, а не угадываются.

## Полный автоматический цикл (v6)

Одна локальная команда запускает геометрию, OCR, углонезависимую привязку размеров и формирует DXF-слой подтверждённых автоматикой размеров:

```bash
python src/auto_pipeline.py photo.jpg output/job --scale-mm=1830
```

Основные результаты: `draft.dxf`, `dimensions_overlay.dxf`, `pipeline_manifest.json`, `ocr_candidates.json`, `dimension_links.json` и диагностические изображения. Автоматические размеры записываются отдельно от режущей геометрии; связи `review` и `unresolved` в DXF не наносятся. Флаг `safe_for_cnc` намеренно остаётся `false`, пока нет операторского подтверждения.
